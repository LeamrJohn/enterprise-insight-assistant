# Enterprise Insight Assistant 完成交付与教学计划

## 摘要

以 `docs/backend_product_delivery_plan.md` 为交付依据，按“先恢复真实基线，再完成区域销售下降闭环，最后按同一架构扩展其余场景”的顺序推进。当前仓库已有 FastAPI、文档处理/RAG、受控 SQL 基础、Celery、Planner/Data/Knowledge/Reviewer 和 LangGraph 骨架；但任务接口仍是旧 `/tasks` 契约，Worker 保存的是旧式 `answer` 工作流结果，Data Agent 仍允许模型生成候选 SQL，固定查询注册表尚未成为主链。

默认认证决策：MVP 前期保留 API Key，但改为安全存储哈希值；不在“区域销售下降”主链前扩展 JWT。此为交付文档提供的明确选项，待主链稳定后再决定是否迁移 JWT。

## 0. 先恢复可验证工程基线

- 先由学习者预测 Ruff 与非 E2E 测试结果，再依次执行 `ruff format`、`ruff check`、目标测试、非 E2E 全量测试；记录通过、失败、未执行项目及每项证明边界。
- 以当前工作区代码和首次实际命令输出为准，重新确认交付文档中“128 通过、4 失败、Ruff 1 错误”的历史基线是否仍成立；不得将该数字写成当前事实。
- 修复首个失败的真实根因，不通过跳过、弱化断言或删除测试恢复绿色；确认 Alembic 只有一个 head、Compose 环境变量有效。
- 创建并验证业务库只读账号：只授予固定业务查询所需表的读取权限，写入尝试必须失败。
- 教学产出：学习者解释一个真实失败堆栈，区分代码、依赖、数据库、Redis、Worker 与测试替身边界；用 `git diff` 说明最小修复。

验收：Ruff 与非 E2E 测试全绿；Compose 配置可验证；只读账号不能写业务库。

## 1. 统一分析任务与结构化报告契约

- 新建/演进分析任务请求契约：第一阶段只允许 `regional_sales_decline`，包含问题、区域、当前月、对比月、允许访问的 `document_ids`；仅在对应场景完整交付后才扩展其他 `Literal`。
- 用明确的 `RunStatus`、`RunStage` 替代当前旧 RAG 阶段枚举；状态覆盖 queued、running、completed、partial、failed、cancelled，阶段覆盖 planning 到 saving_result。
- 将当前 `FinalAnalysis` 演进为交付文档规定的 `FinalAnalysisReport`：`schema_version`、`scenario`、摘要、`ConfirmedFact`、`Hypothesis`、`Recommendation`、`DataEvidence`、`DocumentCitation` 与 `Limitation`。不再把内部 LangGraph State 原样返回给 API。
- 固化报告可信度约束：事实必须关联数据证据；假设必须关联事实和当前用户文档 chunk；建议必须关联事实或假设；数据、资料、模型、引用或结构问题必须形成限制或失败，不能伪装为完成。
- 补充模型、迁移和 Repository：将分析输入、状态/阶段、重试次数、Celery ID、幂等键、错误、时间字段、任务文档范围、证据与报告分别持久化；报告 JSONB 必须先经 Pydantic 校验。
- 将文档 SHA256 从全局唯一迁移为 `(user_id, sha256)` 联合唯一，避免跨用户暴露“同文件已存在”的信息。

教学切片：先由学习者写输入、输出、状态组合、异常和测试场景；随后审查 ORM Model、Pydantic Schema、迁移、Repository 的职责边界。
验收：非法 completed/partial/failed 组合被拒绝；迁移可升级；用户隔离、持久化和 API 序列化测试通过。

## 2. 完成分析任务 API 与事务边界

- 逐步将 `/tasks` 演进为 `/analysis-runs`，提供创建、列表、详情、取消和重试；保留旧接口仅作为明确的短期兼容层，完成迁移后删除，不让两套契约长期并行。
- `POST /analysis-runs` 只做 Schema 校验、当前用户鉴权、文档归属校验、创建任务、提交数据库事务、调用 `.delay()` 并返回 `202 Accepted`；不得在 HTTP 请求内查业务库、Embedding、调用模型或跑工作流。
- 任务文档范围必须在创建时持久化；Worker 只使用服务器保存的 user、范围与参数，不信任客户端再次传入的用户身份或文档 ID。
- 投递失败时保存 `queue_publish_failed` 类错误并允许重新投递；不得返回伪完成结果。先采用“提交后投递”边界，Outbox 仅作为后续可靠性增强，不提前扩大本轮范围。
- 取消接口写入取消状态；Worker 在每个不可逆阶段前用自己的 Session 重新读取状态，取消后不得写 completed/partial 最终报告。
- 认证保持 API Key 路径，但将明文比对改为哈希存储与验证；所有资源继续使用当前用户范围查询，跨用户统一返回 404。

验收：创建返回 202；任务提交早于 `.delay()`；第二用户不能读取、取消或重试第一用户任务；投递失败、取消、不可取消终态和重试入口均有集成测试。

## 3. 以“区域销售下降”完成受控经营数据链路

- 以现有 `DataRequest` 和业务查询注册表为起点，完成两个固定查询：区域销售比较、客户销售下钻；固定种子数据必须能产生可复现的差额、变化率和主要下降客户。
- 新建 `TemplateQueryTool`：只接收已登记 `query_id + parameters`，在仓库内编译 SQL，采用参数化执行、只读事务、超时和行数限制；允许固定查询内部 CTE，不经过当前禁止 CTE 的通用 SQL 校验器。
- 逐步从主分析链移除“LLM 生成 SQL → SQLTool 执行”的路径。用户和模型都不能传入 SQL；通用 SQL AST 校验可保留为独立安全组件，但不是 MVP 分析数据源。
- Planner 输出规范化问题、场景、区域/时间范围、查询 ID、检索范围及资料不足时允许 partial 的策略；Planner 不生成业务结论。
- Data Agent 只调用 `TemplateQueryTool`，返回有 query ID、版本、参数、结果、行数、执行时间的 `DataEvidence`。
- 新增确定性 Fact Builder：从受控查询结果计算指标、变化额、变化率与客户下钻事实；LLM 不计算数字、不把 SQL 原始行自由改写为事实。

验收：正常指标、NULL、除零、空结果、非法参数、超时、写入语句拒绝、越权表拒绝均被覆盖；固定数据可重复得到同一事实；任何入口均不能提交原始 SQL。

## 4. 完成当前用户文档证据链

- 分析任务只检索其持久化的 `document_ids`，同时执行 user 过滤；RAG 返回 chunk、文档、页码、片段、分数和本次允许的 chunk ID 集合。
- 保留现有 Top-K、阈值、关键词/覆盖度充分性判断，并将结果统一为“成功”“资料不足”“技术失败”；资料不足时禁止生成原因性结论。
- Knowledge Agent 只访问 RAG Tool，不访问经营库；模型生成只能使用本次允许 chunks，引用校验失败最多进行一次受控修复，仍失败则降级为资料不足。
- 文档充分时，输出带真实引用的原因假设；仅数据成功但文档不足时保留事实并输出 partial 与补充资料建议，不将建议写成确定归因。

验收：目标 chunk 可检索；跨用户或任务范围外文档不返回；低相关/空资料得到空引用和明确限制；伪造或越界 chunk ID 被拒绝。

## 5. 统一工作流、报告生成与确定性校验

- 将工作流 State 改为结构化计划、Agent 结果、证据、警告、错误分类和最终报告，不再依赖 `final_answer` 作为唯一产物。
- 调整 LangGraph 路由：Planner 后按结构化计划进入 Data、Knowledge 或受控终态；Data/Knowledge 的成功、空结果、资料不足、可重试与不可重试结果共同决定后续路径。
- 保留已有 Planner、Data、Knowledge、Reviewer 角色，但明确边界：Planner 只计划；Data 只固定查询；Knowledge 只 RAG；Reviewer/Composer 只综合已验证证据，不新增事实；确定性校验器最终裁决。
- 实现 Report Composer 生成报告草稿，并接入 Schema、引用存在性/权限、事实—数据证据、假设—文档引用、建议—事实/假设、数字与状态契约校验。
- 按文档处理结果组合：双证据充分为 completed；一侧可靠、另一侧失败或资料不足为 partial；两侧均证据不足时给出拒绝归因的结果；真实依赖故障重试耗尽才为 failed；证据冲突必须保留冲突并输出 partial。
- 保存经过验证的 `FinalAnalysisReport`、摘要和证据引用后，再更新任务终态；报告写入必须具备幂等保护，重复投递/重启/重复点击不得生成重复报告。

验收：报告包含事实、假设、建议、证据与限制；假引用、无依据建议、错误数字和非法状态被拒绝；数据成功而资料不足时不丢事实；重复执行不重复写报告。

## 6. 接通真实 Celery 闭环与故障处理

- Worker 用独立 `SessionLocal()` 读取已提交任务，原子认领任务，依次更新规划、查数、检索、事实构建、报告、校验和保存阶段。
- 按错误分类重试：模型限流、短暂网络/数据库/Redis 故障可重试；请求 Schema、权限、未支持场景、危险 SQL、文档不存在和引用造假不可重试。
- 记录 request_id、user_id、analysis_run_id、stage、attempt_count、error_type、duration_ms；禁止记录 API Key、密码、完整敏感文档与未脱敏联系方式。
- 建立真实 E2E：API 创建任务 → 平台库 commit → Redis → 独立 Worker → 只读业务库 → pgvector → Gateway 替身或受控测试配置 → 报告持久化 → GET 查询。`.run()` 与 mock 测试只证明进程内逻辑，不能替代此链路。

验收：真实 Worker 消费、独立 Session 可见性、取消不覆盖终态、分类重试、幂等写入和最终报告查询均有证据；日志可定位失败阶段。

## 7. 按同一模板扩展另外三类场景

按顺序交付：毛利下降、客诉上升、应收风险。每个场景单独完成以下最小闭环后才开始下一个：

- 明确固定问题范围、业务口径与禁止误述；应收风险不得把逾期直接说成坏账。
- 增加请求支持、Planner 计划、DataRequest、固定查询、受控 Fact Builder、文档检索策略、报告建议与限制。
- 建立可重复种子数据、正常/空/异常测试和一个固定评测案例。
- 通过用户隔离、引用、数字、取消、重试与 E2E 回归后，才扩展 `scenario` Literal。

## 8. 安全、可观测、评测、部署与最小前端

- 安全：完成 API Key 哈希化、限流、敏感字段脱敏、提示注入与越权 Tool 调用测试；不让 LLM 决定权限或执行用户 SQL。
- 可观测：实现任务失败查询、日志关联与阶段耗时；用真实日志演示一次定位流程。
- 评测：固定五个案例——四类业务场景加“数据存在但原因文档不足”；统计查询参数正确率、数据事实正确率、引用有效率、数字一致率、拒答正确率、报告 Schema 有效率、工作流完成率、P50/P95 与模型 Token/成本。仅在获得真实基线后设目标值。
- 部署：验证从零 Docker Compose 启动、迁移、健康检查、业务数据初始化与只读账号；编写 PostgreSQL、Redis、Worker、模型故障的最小 Runbook，以及备份恢复验证。
- 前端最后实现最小必要页面：登录/身份入口、文档知识库、分析工作台、任务进度和报告展示；只展示后端已持久化的状态、事实、引用和限制，不新增独立业务逻辑。

## 固定教学与完成标准

每个切片都遵循：心智模型（调用者→输入→处理→输出→失败→保存者）→ 学习者先写契约/测试场景 → 实现 → Ruff → 单元测试 → 集成测试 → 必要时 E2E → 数据库和日志检查 → 复盘。

每次结束必须记录：执行命令、通过/失败/未运行项、测试实际证明与未证明的边界。掌握状态分别按“解释、修改、验证、排错”评定；代码存在或测试通过不能直接判定为学习者“能独立交付”。

最终 MVP 验收：用户 A 上传至少两份文档，创建区域销售下降任务并收到 202；独立 Worker 以只读业务账号取证，报告至少含一条可验证事实、一条真实文档支持的假设和一条有依据的建议；资料不足为 partial、真实技术失败为 failed；用户 B 无法访问 A 的数据；重复投递不重复出报告；取消不保存最终结果；日志可定位阶段；Docker 可从零启动；学习者可完整解释、修改、验证并排查全链路。
