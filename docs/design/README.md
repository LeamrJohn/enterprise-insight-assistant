# 模块设计稿

每个模块在改造前先在本目录写一页设计稿，评审通过后再写代码。文件名用模块名，例如 `memory.md`、`tool_layer.md`、`task_state_machine.md`。

方法来源：[改进与学习计划第 1 节](../plans/improvement_and_learning_plan.md)。

## 模板

```markdown
# <模块名> 设计稿

- 状态：草稿 / 评审中 / 已通过 / 已实现
- 作者：
- 评审：
- 关联阶段：

## 0. 现状与问题
现在怎么工作（调用链：源函数 → 目标函数 → 字段 → 写入），哪里不符合生产标准，有什么证据。

## 1. 职责与边界
负责什么、不负责什么、谁调用它。

## 2. 数据模型与生命周期
表、字段、索引、唯一约束；创建 → 更新 → 过期 → 删除。

## 3. 接口契约
输入输出（Pydantic）、版本号、固定错误码。

## 4. 状态机
状态列表与合法转换表。

## 5. 权限
谁能读写；在哪一层强制。

## 6. 失败模式
超时、重复、并发、部分失败、依赖不可用时的行为。

## 7. 资源上限
条数、Token、时间、并发、存储。

## 8. 一致性与幂等
事务边界、幂等键、重试是否安全。

## 9. 可观测
事件、指标、日志中禁止出现的内容。

## 10. 测试
单元 / 契约 / 集成（真实 PG）/ 故障注入 / 评测 Case 清单。

## 11. 运维
迁移与回滚、定时任务、配置项、数据修复手段。

## 12. 安全
不可信输入、敏感数据、注入、数据外发。

## 迁移与回滚
从现状到目标的步骤；每步如何回退。

## 未证明范围
这份设计不保证什么。
```

## 完成定义（DoD）

设计稿通过 → 迁移可升级也可回滚 → 契约测试 + 真实 PG 集成测试 + 至少 2 个故障注入测试通过 → 有事件和指标 → CI 全绿 → `evidence.md` 记录已证与未证。
