## 0. 目标（我对你要求的理解）

1. **项目目标**：把整个项目的每个模块、每个地方，按企业项目的生产标准重新设计和实现。不上线，但不是 demo。
2. **个人目标（底线）**：学会 Agent 开发和标准的生产级开发；以后面对一个新模块，能**自己**设计到生产标准、实现、测试、排错。
3. **由此推出的原则**：
   - 标准不降，范围不砍；顺序按依赖关系排。
   - 每个模块都用**同一套设计方法**改造。你学的是这套方法，模块只是练习场。
   - 你在项目里的角色逐步从“照着做”变成“自己设计，我来审”。

“生产标准”在这里的含义：每个模块都有明确的职责、数据生命周期、接口契约、状态与失败处理、权限、资源上限、可观测、测试和运维方案。它不等于 K8s、微服务或高可用集群。

## 1. 通用方法：生产级模块设计模板（核心教学内容）

以后任何模块，先用这 12 个问题写一页设计稿，评审通过后再写代码。这就是“自主设计能力”的具体形态。

| # | 问题 | 要写清楚的东西 | 例子（记忆模块） |
|---|---|---|---|
| 1 | 职责与边界 | 负责什么、不负责什么、谁调用它 | 只提供历史线索，不提供当前事实 |
| 2 | 数据模型与生命周期 | 表、字段、索引、唯一约束；创建→更新→过期→删除 | 写入、合并、过期、撤回、物理清理 |
| 3 | 接口契约 | 输入输出用 Pydantic 定义，有版本号，错误码固定 | `MemoryCandidate` → `MemoryWriteDecision` |
| 4 | 状态机 | 合法状态和合法转换，用一张表写死 | `candidate → active → superseded / expired / revoked` |
| 5 | 权限 | 谁能读写；在哪一层强制（数据库 / 服务 / API） | 读取时按当前成员身份与来源文档权限再过滤 |
| 6 | 失败模式 | 超时、重复、并发、部分失败、依赖挂掉时怎么办 | 写入重复由幂等键挡住；整理任务中断后可重跑 |
| 7 | 资源上限 | 条数、Token、时间、并发、存储的上限 | 每用户活跃记忆 ≤ N 条，注入 ≤ 1024 Token |
| 8 | 一致性与幂等 | 事务边界、幂等键、重试是否安全 | 同一报告只生成一次记忆 |
| 9 | 可观测 | 打哪些事件、哪些指标、日志不能出现什么 | 选中 / 舍弃原因写入 manifest，正文不进日志 |
| 10 | 测试 | 单元、契约、集成（真实 PG）、故障注入、评测 | 过期、撤权、冲突、跨用户、注入 |
| 11 | 运维 | 迁移与回滚、定时任务、配置项、数据修复手段 | 定时整理任务、可手动重跑、可开关 |
| 12 | 安全 | 不可信输入、敏感数据、注入、数据外发 | 记忆内容视为不可信，不能改变系统规则 |

**完成定义（DoD），每个模块都一样**：设计稿评审通过 → 迁移可升级也可回滚 → 契约测试 + 真实 PG 集成测试 + 至少 2 个故障注入测试通过 → 有事件和指标 → CI 全绿 → evidence 记录已证与未证。

## 3. 目标设计（每个模块要改成什么样）

### 3.0 改造后的整体运行链路（★ 为新增或重写）

```
① 入口  前端 → API
   ★ 认证：访问令牌 + 刷新令牌 + 令牌版本号（改密/禁用即失效）
   ★ 限流与背压：按用户/公司限制请求数与排队数，超限返回 429
   → 创建任务（一个事务）：用户消息 + 任务 + Outbox 事件 + 占位回复
     ★ 冻结范围：按“部门/个人授权”算出可见文档与数据源
     ★ 冻结运行版本：Prompt、模型与参数、工具契约、工作流版本
     ★ 生成 trace_id，贯穿后续所有环节

② 投递  Outbox → 队列；★ 对账任务；★ 死信表（可人工查看、重放）

③ Worker  ★ 三级状态机：任务 / 执行尝试（租约 + fencing token）/ 节点
   ★ 所有转换走同一函数和转换表，数据库 CHECK 约束兜底
   ★ 任务级截止时间 + 统一预算（Token、费用、工具次数、总时长），跨重试共享

④ 每个节点的统一执行方式
   ★ Context Builder（模型调用的唯一入口）：
       系统规则 > 任务约束 > 当前问题(关键实体/时间受保护) > 短期记忆 > 长期记忆 > 证据 > 输出预留
       分层预算、低优先级先压缩、不可信内容隔离、ContextManifest 持久化
   模型网关：调用前预留、调用后结算，超时、错误分类、显式回退
   ★ 工具层：注册表 → 按 A/B/C/D 等级执行
   节点完成 → Checkpoint（快照 + 版本 + 输入指纹）
   ★ 防死循环四道闸：步数上限 / 重复状态检测 / 预算熔断 / 截止时间
   ★ 取消：节点在下一检查点停止，迟到结果被 fencing 拒绝

⑤ 业务节点
   Planner → 结构化计划（意图、指标、时间口径、所需证据）
   Data → SQL ★AST 白名单 + 语句超时 + 行数/字节上限 → 只读执行
          ★ 指标口径集中定义、Decimal 计算、数字血缘（查询/行/列）
   Knowledge → ★ 授权前置过滤 → 召回 → 重排 → 证据“支持/反驳/不足”判定，冲突与时效检查
   Reviewer → 草稿，★ 每条结论绑定证据 ID

⑥ ★ 发布门禁（确定性）
   数字复算 → 引用在授权范围内 → 无证据结论降级为假设或删除
   → 发布前复核当前权限 → 唯一发布约束 → 写入报告与终态

⑦ ★ 发布后  记忆候选 → 写入门禁 → 长期记忆；更新会话摘要；生成评测 Observation

⑧ ★ 后台定时任务
   Outbox 投递/对账、租约回收（已有）
   ★ 记忆整理（合并去重、冲突、取代、衰减）、过期物理清理、删除传播、异步作业超时回收
```

### 3.1 记忆：三层 + 完整生命周期

| 层 | 存什么 | 存在哪 | 生命周期 |
|---|---|---|---|
| 工作记忆 | 本次任务执行状态：计划、中间结果、已用预算 | Checkpoint（PostgreSQL） | 随任务结束冻结；只用于恢复，不跨任务 |
| 短期记忆 | 会话摘要、指代对象（“这个产品”指什么）、本会话已确认的条件 | 新表 `conversation_memory`，按会话 | 会话不活跃 N 天后过期；每 K 轮或超出 Token 时增量摘要，摘要必须保留来源消息 ID |
| 长期记忆 | 用户偏好、已验证的业务事实线索、常用口径 | `AnalysisMemory` 扩展：类型、重要度、来源版本、embedding、状态 | 写入门禁 → active → 合并/取代/过期/撤回 → 物理清理 |

关键机制：

- **写入门禁**：只从已发布报告或用户明确确认的内容生成候选；规则检查（来源、权限、敏感字段）通过才写入；带幂等键。
- **读取**：先按当前权限和有效期过滤，再按“相关性 × 时效 × 重要度”打分，在 Token 预算内选取，输出 manifest。记忆只做线索，当前数字必须重新查库。
- **定时整理（Celery beat 新任务）**：去重合并相似记忆、标记冲突、旧事实被新事实取代、重要度衰减、清理过期和已撤回的数据。任务可重跑（幂等）、有处理水位、可开关。
- **删除传播**：来源文档被删除或撤权、用户被移出公司时，相关记忆立即失效。
- **用户可控**：API 可查看、删除自己的记忆。

### 3.2 工具层：按“风险和代价”分级，而不是按大小

先修正一个概念：**Skill 和 MCP 都不能解决“耗时长”**。

- **MCP** 是一个协议和进程边界：适合独立维护、要被多个客户端共享、或需要进程隔离的工具。它本身不会让工具变快或变安全。
- **Skill** 是“流程知识包”（如“销售下滑分析流程”：步骤、所需工具、指标口径），不是执行器。
- **耗时长**要靠**异步作业模式**解决：提交 → 返回 job_id → 后台执行 → 进度/心跳 → 可取消 → 结果持久化。

工具分级规则：

| 级别 | 判定 | 实现方式 | 例子 |
|---|---|---|---|
| A 内联工具 | < 1 秒、纯计算、无外部依赖 | Agent 进程内函数，仍走 ToolRuntime | 日期解析、单位换算、Decimal 计算 |
| B 同步受控工具 | 秒级、访问内部资源 | ToolRuntime + 单次超时 + 错误分类 + 有限重试 | SQL 查询、RAG 检索 |
| C 异步作业工具 | 可能 > 30 秒、资源占用大 | 作业表 + Celery 队列 + 进度 + 取消 + 结果引用 | 大文档解析、OCR、大批量重算 |
| D 外部/隔离工具 | 独立维护、第三方系统、需要进程隔离 | MCP 适配器，仍必须经过 ToolRuntime 的权限、预算、审计 | 外部 ERP 只读查询、现有证据 MCP 工具 |

所有级别共用：工具注册表（名称、版本、输入输出 Schema、预期耗时、成本、副作用类型、权限要求）、服务端注入授权参数、超时与取消、结果大小上限、调用记录。Skill 作为流程包单独做：有版本、声明所需工具，但**不能给自己授予权限**。

### 3.3 上下文：分层装配管道

```
系统规则（固定、最高优先级）
→ 任务约束（冻结范围、时间、公司）
→ 当前问题（含解析出的关键实体与时间，受保护不得截断）
→ 短期记忆（会话摘要 + 指代）
→ 长期记忆（相关性选择后的线索）
→ 证据（SQL 结果摘要 / 文档片段，带引用 ID）
→ 输出预留
```

- 每层有独立预算和优先级；超出时从低优先级开始压缩，而不是直接截断最近消息。
- 每个片段带来源 ID、版本、可信度标记；用户输入、文档内容、历史消息一律标为“不可信数据”，用固定分隔格式放入，不能改变规则。
- 压缩策略：结构化数据先转成摘要表；长文档片段取命中段落；历史转摘要。关键数字、否定词、时间条件不能被截掉，放不下就请用户澄清或明确失败。
- 输出 ContextManifest（选了什么、舍弃什么、为什么、各层 Token），随任务持久化，可复现。
- 网关调用前最后再按真实 Token 数复核一次。

### 3.4 任务状态机：三级状态 + 四道防循环

| 级别 | 状态 | 负责什么 |
|---|---|---|
| 任务 Task | queued / running / awaiting_review / retrying / completed / partial / needs_clarification / failed / cancelled | 用户看到的生命周期 |
| 执行尝试 Attempt | claimed / running / succeeded / failed / lease_expired / superseded | 哪个 Worker 有执行权（租约 + fencing token） |
| 节点 Node | pending / running / succeeded / failed / skipped | 图中每一步的结果与 Checkpoint |

- 所有转换都只能通过一个函数，查同一张转换表；非法转换报错并记事件。数据库加 CHECK 约束兜底。
- **断点恢复**：每个节点完成后写 Checkpoint（状态快照 + 版本 + 输入指纹）；恢复时版本不兼容就从安全节点重跑；每个节点声明“可重入”或“需补偿”。
- **防死循环四道闸**：
  1. 图步数上限（已有，20）；
  2. 重复状态检测：同一节点 + 同一输入指纹出现第二次即停止或换策略；
  3. 统一预算熔断：Token、费用、工具调用次数、总时长，跨重试共享；
  4. 截止时间：任务级 deadline，超过就以 partial / failed 结束并写明原因。
- 取消：用户取消后，正在执行的节点在下一个检查点停止；迟到的结果被 fencing 拒绝写入。

| 文档与 RAG | 文档版本 + chunk hash；摄取状态机；索引一致后才可见；删除传播；证据判断“支持/反驳/不足”；检索指标与回答指标分开评测 |
| 报告与发布 | 每条结论绑定证据 ID；数字由代码复算；证据不足自动降级；唯一发布约束；拒绝原因可解释 |
| 人工审核 | 审批绑定草稿 hash；审核人权限实时校验；过期与重复审批拒绝 |
| 模型网关 | 价格表按供应商 + 模型；调用前预留、调用后结算，失败时状态为“未知”而不是 0；错误分类（可重试/不可重试）；显式回退 |
| 异步与投递 | Outbox 对账；死信队列；队列长度上限与背压；Celery 任务幂等 |
| 可观测 | 统一 trace_id 贯穿 API → Worker → 节点 → 工具 → 模型；JSON 结构化日志并脱敏；关键指标（成功率、P95、费用）与告警 |
| 评测 | 开发集 + 密封留出集；CI 跑快速回归；改动前后对照报告 |
| 配置与密钥 | 分环境配置；启动时校验；密钥轮换流程 |
| 数据库运维 | 迁移可降级并测试；定时备份；恢复演练有 RTO/RPO 目标 |
| 前端 | 加载/错误/空状态；证据可点击溯源；权限不足提示；会话与记忆管理界面 |
| 部署 | Docker 镜像可复现构建；健康检查区分存活与就绪；一键启动 + 自检脚本；依赖漏洞扫描 |

## 4. 改进路线（按依赖排序）

每周约 20 小时，含学习时间。估算总量约 **500–600 小时，约 7–8 个月**。这是诚实估计：边学边做，全项目达到生产标准就需要这么久。时间少则顺延，不砍标准。

| 阶段 | 周 | 内容 | 为什么排在这里 |
|---|---|---|---|
| 1 工程基础 | 1–2 | 分批提交现有改动；CI；pre-commit；测试分层；分支与 PR 流程 | 后面每一步都依赖“能安全地改、能自动验证” |
| 2 评测基线 | 3–4 | 30 例评测（23 开发 + 7 密封留出，留出由你编写并放在仓库外）；基线报告 | 没有基线，就无法证明改造没有变差 |
| 3 任务状态机 | 5–7 | 三级状态、四道防循环、Checkpoint 恢复、取消 | 所有 Agent 能力都运行在它上面 |
| 4 工具层 | 8–10 | 注册表、分级、超时与取消、错误分类、异步作业；MCP 适配器纳入统一规范 | 上下文和记忆都要通过工具拿数据 |
| 5 上下文 | 11–12 | 分层装配管道、压缩、manifest、Token 复核 | 依赖工具结果的结构化格式 |
| 6 记忆 | 13–16 | 三层记忆、写入门禁、相关性检索、定时整理、删除传播、用户管理 | 依赖上下文管道作为唯一注入口 |
| 7 权限与数据源 | 17–20 | 部门/文档授权、加密凭据、自助接入、令牌撤销 | 产品核心诉求；此时你已能独立完成大部分 |
| 8 SQL / RAG / 报告 | 21–25 | 指标口径、数字血缘、证据判断、发布门禁、人工审核 | “不胡说”的最终保证 |

| 10 毕业项目 | 30–32 | 你**独立**设计并实现一个新模块（建议：上传模块按同样标准重做，或一个新的只读工具） | 证明你已具备自主设计能力 |

上传/附件模块在第 10 阶段之前保持冻结、关闭入口，不以半成品开放。

## 5. 教学计划

### 5.1 能力交接三阶段

| 教学模式 | 适用阶段 | 设计谁来做 | 代码谁来写 | 我的角色 |
|---|---|---|---|---|
| 示范 | 1–3 | 我写设计稿，逐条讲 12 个问题 | 我写骨架，你写关键函数与测试 | 讲解 + 审查 |
| 共同设计 | 4–7 | 你先写设计稿，我指出漏洞 | 你写主体，我只补样板代码 | 设计评审 + 代码审查 |
| 自主 | 8–10 | 你独立设计 | 你独立实现 | 只做验收；不给答案，只提问 |

### 5.2 每个模块的固定学习循环

1. **读现状**：你画出调用链（源函数 → 目标函数 → 字段 → 写入），我批改。
2. **找差距**：用 12 个问题逐条对照现状，写出差距清单。
3. **写设计稿**：一页纸，存为 `docs/design/<模块>.md`。
4. **设计评审**：我挑问题；通过后才写代码。
5. **先写测试**：契约测试和失败场景测试先写，此时应失败。
6. **实现**：小步提交，每次提交都让 CI 变绿。
7. **故障注入**：自己制造一次失败（超时、重复、崩溃、撤权），看系统是否按设计应对。
8. **复盘**：写入 evidence：已证、未证、学到的可迁移规律。

### 5.3 各阶段要学的知识

| 阶段 | 技术知识 | 生产工程知识 |
|---|---|---|
| 1 | git 分支/提交/回退、GitHub Actions、ruff、pyright、pytest fixture 与 marker | 为什么要 CI 门禁；测试金字塔 |
| 2 | JSON Schema、Pydantic、评测指标计算 | 基线与候选、开发集与留出集、为什么不能自证 |
| 3 | 状态机、LangGraph 条件边、SQLAlchemy 事务、行锁 | 幂等、租约与 fencing、断点恢复、熔断 |
| 4 | Protocol / 抽象类、超时与取消（线程/进程/asyncio）、Celery、MCP SDK | 错误分类、重试退避、异步作业模式、进程隔离 |
| 5 | tiktoken 计数、Prompt 结构、摘要 | 预算分配、不可信输入隔离、可复现 |
| 6 | pgvector 相似度、Celery beat 定时任务 | 数据生命周期、TTL、软删除与物理删除、删除传播 |
| 7 | Alembic 迁移、RLS、加密（cryptography/Fernet）、JWT 刷新 | 最小权限、密钥管理、权限审计 |
| 8 | sqlglot AST、Decimal、RAG 评测指标 | 正确性门禁、可追溯性、人工审核流程 |
| 9 | 结构化日志、指标、pg_dump/恢复 | 可观测三要素、RTO/RPO、事故复盘 |
| 10 | 综合 | 从零完成一份生产级设计并落地 |

### 5.4 掌握度判定

- **讲得清**：能按调用链讲出职责、数据、失败边界。
- **带着改**：给了约束后能写出代码和测试。
- **独立做**：新场景里自己完成“设计 → 实现 → 测试 → 排错”。

每个阶段结束时做一道没见过的验收题（例如“给会话摘要加一个过期策略”），用来判定是否到“独立做”。测试通过不等于掌握。
