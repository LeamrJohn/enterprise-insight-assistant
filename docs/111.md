多公司经营智能聊天系统：缺失能力与优先级路线
1. 目标与完成标准
目标是在本地 Docker 环境中运行一个面向多个公司的经营智能聊天系统。
每家公司必须拥有独立的业务数据库连接、独立的文档空间和独立的成员权限。用户在公司上下文中用自然语言提出经营问题，系统在只读、租户隔离和证据约束下完成数据查询与文档检索，并输出可追溯的经营回答。
回答必须区分：
已确认事实：只能来自受控经营数据。
原因假设：必须有当前公司授权文档引用，并明确不是确定因果。
建议：必须关联事实或假设。
资料不足：系统正常运行，但证据不够，不给出确定归因。
系统失败：数据源、模型或基础设施不可恢复地失败，不输出经营结论。
预测：必须和历史事实分开展示，注明预测范围、方法、置信程度和局限。
追问：问题缺少指标、时间、区域、对象或分析口径时，系统主动提出明确问题，并在用户补答后继续同一分析。
完成不等于接口、模型或测试文件存在。完成必须同时满足：Docker 能从零启动；真实 API、Redis、Worker、数据库和模型链路可运行；公司 A 与公司 B 的数据和文档不能串；最终结果可查询、可回溯；关键失败路径有自动化测试和真实环境验证。
2. 当前已有基础
当前项目已有多公司方向的初步结构：
已有公司、公司成员、业务数据源和 Schema 快照模型。
已有公司成员检查，以及创建数据源和发现 PostgreSQL Schema 的接口。
会话、分析任务和文档已能关联公司。
已有文档分块、向量检索、Celery Worker、LangGraph、Planner、Data Agent、Knowledge Agent 和 Reviewer 骨架。
已有只读 SQL 执行、SQL 校验、超时、最大行数、部分字段脱敏和 Schema 快照校验。
已有结构化报告契约，能表达事实、假设、建议、数据证据、文档引用和限制。
Docker Compose 已包含 API、Worker、Redis、平台数据库和两个演示业务数据库。
这些基础证明项目不是从零开始，但它们尚未组合为“多公司分析任务到可信报告”的完整闭环。
3. P0：先完成统一的公司级分析任务契约
这是当前最优先的工作。
需要建立正式的 AnalysisRun 或演进现有 AnalysisTask，统一承载一次公司级经营分析。不要继续让旧 /tasks、会话消息和 Worker 各自保存不同形状的数据。
一次分析任务至少需要保存：
company_id
data_source_id
schema_snapshot_id
user_id
原始问题
已澄清的问题
用户选定或系统限定的 document_ids
分析场景或分析意图
执行状态
当前执行阶段
结构化报告
错误分类
重试次数
追问状态和待补字段
创建、开始、完成时间
建议接口统一为：
POST /analysis-runs
GET /analysis-runs
GET /analysis-runs/{id}
POST /analysis-runs/{id}/cancel
POST /analysis-runs/{id}/retry
POST /analysis-runs/{id}/clarifications
创建任务时必须在同一个事务中完成：
验证当前用户是公司成员
→ 验证数据源属于该公司
→ 验证 Schema 快照属于该数据源
→ 验证文档属于当前用户和当前公司
→ 创建任务及其文档范围
→ commit
→ 再投递 Celery
验收标准是：用户 B 无法以任何接口读取、创建、取消或重试用户 A 公司下的任务；Worker 用独立 Session 能读到已提交任务；任务结果只通过统一接口返回。
4. P0：明确“自动理解数据表”后的受控查询策略
“系统自动理解公司数据表”不能等于“模型可以自由执行 SQL”。
当前项目同时存在模板查询和模型生成候选 SQL 两条路线，必须明确主路线，避免权限边界模糊。
建议采用“受约束自由 SQL”作为多公司目标：
公司管理员配置只读数据源
→ 系统发现并保存 Schema 快照
→ 管理员或系统维护业务语义目录
→ Planner 生成结构化数据请求
→ Data Agent 只生成 SQLCandidate
→ 确定性校验器检查 AST、表、字段、关联、聚合、限制条件
→ 只读账号执行
→ 保存查询、参数、快照版本、结果摘要
必须补齐以下能力：
Schema 快照版本冻结，任务执行时不能悄悄切到新 Schema。
每家公司维护允许查询的表、字段、关联关系和敏感字段策略。
模型只能看到脱敏后的 Schema 目录，不能看到密码、连接串或任意环境变量。
禁止 DDL、DML、跨 Schema、系统表、危险函数、递归查询和超范围 JOIN。
强制查询超时、最大扫描量、最大返回行数、最大查询次数和最大修复次数。
每次查询写入审计记录：公司、任务、快照、SQL、参数、耗时、行数、结果状态。
对高风险字段执行字段级脱敏或直接拒绝。
所有业务数据库账号必须是真实 PostgreSQL 只读账号，而不仅是应用层 READ ONLY。
TemplateQueryTool 可以保留，用于常见、口径稳定的指标；但不能和另一条查询路径互相绕过权限控制。两种路径都必须使用同一公司数据源、同一只读账号和同一审计链路。
验收标准是：对两个不同公司数据库执行同一类问题时，查询只能命中各自 Schema 快照允许的表；写入 SQL、越权表、越权字段和非法 JOIN 都被拒绝；只读数据库账号的真实写入尝试失败。
5. P0：完成结构化报告的持久化与可信输出
当前报告契约已经出现，但 Worker 仍主要保存工作流中间数据和文本答案。最终用户产物必须从“字符串回答”升级为“可验证报告”。
需要增加或明确持久化边界：
WorkflowState
→ FinalAnalysisReport
→ Schema 校验
→ 引用校验
→ 数字校验
→ 保存报告与证据
→ 更新任务状态
→ API 返回报告
报告至少包含：
outcome：completed、partial、insufficient_evidence。
执行状态：queued、running、retrying、completed、failed、cancelled。
已确认事实及其数据证据 ID。
数据证据，包括查询用途、Schema 快照版本、参数、字段、结果摘要。
原因假设及其文档 chunk 引用。
建议及其事实或假设依据。
限制、冲突和下一步补充材料建议。
预测结果及其预测元数据；预测不能混入事实列表。
必须坚持以下规则：
文档不能单独证明经营数字。
数据不能单独证明业务原因。
没有文档引用时，只能给数据事实和核查建议。
文档与数据冲突时输出 partial，不能让 Reviewer 自行选一方为真。
文档不足是正常业务结果，不是系统 failed。
技术失败不能伪装成资料不足。
Reviewer 只能综合已验证证据，不能创造新事实。
验收标准是：编造 chunk_id、错误数字、无依据建议和事实/假设混淆均被确定性校验器拒绝；API 可以从持久化报告中直接重建用户展示结果。
6. P0：完成追问与连续对话状态机
当前 Planner 能识别澄清需求，但还缺少可恢复的追问流程。
需要把“追问”视为任务的一个明确结果，而不是一条普通助手文本。任务需要记录：
当前是否等待用户补充。
缺少哪些字段，例如时间、指标、区域、产品、客户、数据源或文档范围。
追问文本。
原始问题和已解析上下文。
用户补答后合成的 resolved_question。
最大追问轮次，避免无限循环。
推荐流程：
用户问题
→ Planner 判断信息是否足够
→ 信息不足：保存 needs_clarification
→ 返回具体追问
→ 用户提交补答
→ 更新同一分析任务或创建带父任务关系的新任务
→ 合成 resolved_question
→ 才进入数据与知识链路
验收标准是：模糊问题不会调用 SQL 或 RAG；补充“华东、2025 年 8 月、销售额、对比 7 月”后，系统能在同一公司和同一文档范围内继续分析。
7. P1：把公司隔离落实到每一层
当前公司关联已进入模型和上层服务，但还需要把隔离变成不可遗漏的默认约束。
需要完成：
文档、分块、向量检索、会话、任务、报告和审计记录都带 company_id。
向量检索 SQL 同时按 user_id 和 company_id 过滤，不能只依赖调用方传入 document_ids。
分析任务创建时锁定公司、数据源、Schema 快照和文档范围；Worker 不重新按“当前最新配置”猜测。
公司成员角色至少区分 owner、analyst、viewer。
owner 才能配置数据源、触发 Schema 发现和管理成员。
数据源密码不存数据库明文；数据库只保存凭据引用。
数据源主机、端口和数据库名必须经过 allowlist 或网络策略限制，避免配置接口成为内网扫描入口。
记录谁在什么时间访问了哪个公司的数据与文档。
验收标准是：跨公司文档、跨公司 chunk、跨公司任务、跨公司数据源和跨公司 Schema 快照访问都返回 404 或拒绝；测试必须覆盖“同一用户属于两个公司”的情况。
8. P1：建立预测能力，但与分析事实严格分离
预测不是把模型提示词改成“预测一下”。它需要独立的数据和质量契约。
第一版建议只支持一个可解释场景，例如“未来一个月区域销售额预测”。
预测模块需要：
明确预测目标、时间粒度、训练窗口和预测窗口。
使用受控数据查询得到时间序列。
先建立简单基线，例如移动平均、季节性朴素预测或线性趋势。
输出预测值、历史区间、置信区间或不确定性说明。
记录数据缺失、异常值、节假日、促销等可能影响。
做回测，记录 MAE、MAPE 或其他适合当前指标的误差。
对数据量不足、结构变化明显或误差过高的情况拒绝预测。
预测报告必须与历史事实分开：
已确认事实：过去已经发生的数据。
预测：基于历史数据的估计，不是事实。
建议：基于事实与预测风险提出的行动。
限制：预测误差、数据不足和外部变化。
验收标准是：预测数字可以回溯到固定训练数据和固定算法版本；系统不会将预测表述为“已经发生”；数据不足时返回无法可靠预测。
9. P1：完成 Docker 从零启动与演示初始化
“容器正在运行”不等于“项目可本地交付”。
需要提供一个从空 Docker 环境开始的可重复流程：
docker compose up --build
→ migrate 完成
→ 演示公司数据库完成 seed
→ 平台创建演示用户、公司、成员关系、数据源和 Schema 快照
→ 上传或导入演示文档
→ 文档 Worker 完成分块和向量化
→ 发起两家公司各自的分析任务
→ 查询最终报告
需要补齐：
初始化服务或幂等脚本。
API、Worker、Redis、平台数据库、演示业务库的健康检查。
API 和 Worker 对迁移、Redis、演示 seed 的正确依赖。
不依赖 GPU 的默认本地模式。
本地模型模式或明确的外部模型 Key 配置说明。
.env.example 的完整说明和安全默认值。
启动、日志查看、任务排错、重置演示数据的 Runbook。
一条自动化 Docker E2E 脚本。
验收标准是：在新机器或清空卷后，按 README 命令可以完成两家公司隔离的端到端演示；不需要手工进入数据库修数据。
10. P2：完善认证、观测、评测和前端
在主链路可信后，再完成这些交付能力。
认证方面需要迁移为安全 API Key 哈希或密码哈希加 JWT，并支持密钥轮换、过期、登出和审计。
观测方面需要把：
request_id
→ user_id
→ company_id
→ conversation_id
→ analysis_run_id
→ celery_task_id
→ query_audit_id
→ report_id
关联起来。日志不能记录数据库密码、完整敏感数据和未经脱敏的文档内容。
评测方面需要建立固定案例集，至少覆盖区域销售下降、毛利下降、客诉上升、应收风险、资料不足、数据故障、模型格式错误、非法 SQL、跨租户访问和文档注入。评测指标至少包括查询成功率、引用有效率、数字一致率、资料不足拒答准确率、任务耗时和成本。
前端方面需要实现公司选择、会话、追问、文档范围选择、任务进度、报告结构化展示、数据证据展开、文档引用跳转、失败和资料不足提示。
11. 建议执行顺序
第一步：统一公司级分析任务与 API 契约。
第二步：让 Worker 使用冻结的公司数据源、Schema 快照和文档范围，跑通一条受控查询和检索链路。
第三步：把结构化报告、证据和状态持久化，并完成 completed、partial、insufficient_evidence、failed 的明确分支。
第四步：完成真实只读账号、公司隔离和查询审计的 Docker E2E。
第五步：完成主动追问与补答后的恢复执行。
第六步：完成一键 Docker 初始化、两个公司演示数据和运行手册。
第七步：在稳定分析链路上增加一个可回测的预测场景。
第八步：补齐认证、观测、评测和前端展示。
当前最短路径仍是第一步：先定义并实现统一的公司级分析任务契约。它决定后续查询边界、文档范围、报告保存、追问恢复、Worker 状态和前端接口如何对齐。
